SLIDE 2: LE PROBLÈME AUQUEL NOUS RÉPONDONS
═════════════════════════════════════════════

Incremental reveal: première couche (titre), puis 3 boîtes rouges, puis solution verte

NOTES (à dire):
"Commençons par les problèmes qu'on voulait résoudre.

Problème numéro 1 - CONFLITS:
Vous connaissez tous Git, c'est l'outil standard pour collaborer.
Mais Git a une limitation: les conflits de merge.
Deux développeurs modifient le même fichier → Git peut pas décider qui a raison.
Quelqu'un doit résoudre le conflit manuellement. C'est frustrant.

Problème numéro 2 - LATENCE:
Les outils collaboratifs actuels comme VS Code Live Share utilisent WebSocket polling.
Ça veut dire 'demander' toutes les secondes: "Quoi de neuf?"
Latence typique: 1-2 secondes. Quand deux personnes tapent en même temps, c'est like
regarder les characters apparaître en delay. Pas fluide.

Problème numéro 3 - OFFLINE:
Connecté à internet? Sans connection = pas de travail. Terrible si votre WiFi fail
ou si vous êtes un 'digital nomad' en avion.

[Pause 2 secondes]

Alors, comment résoudre ces trois problèmes?

La réponse: CRDT. Conflict-free Replicated Data Types.

CRDT c'est un concept de research qui permet à data replicated sur plusieurs machines
de converger vers le même état... même si elles communiquent pas, et même si les
modifications arrivent dans des ordres différents.

C'est comme magic, mais c'est math. Et nous avons implémenté ça en Java."

SLIDE 6: CRDT Core

Affiche comparison avant/après et composants clés

NOTES:
"Le cœur du projet: CRDT Core.

À gauche (problème sans CRDT):
deux clients inserts 'e' et 'a' au même position. C'est ambigü.
Git dit: conflict. Humain must decide.

À droite (avec CRDT):
chaque character gets unique ID. Client A's 'e' a ID #123,
Client B's 'a' a ID #124. Les IDs décident l'ordre automatiquement.
Merge: 'heaello' - les deux inserts sont présent.
Zéro ambiguïté.

Les 5 composants:
1. CRDTIdentifier - unique ID per character
2. CRDTElement - wrapper around character
3. CRDTOperation - action (INSERT/DELETE)
4. CRDTDocument - container of elements
5. CRDTEngine - orchestrates merge

57 unit tests vérify tout fonctionne
Concurrency tests vérify thread-safety
Merge tests vérify convergence"

SLIDE 7: Sync-Server & Optimisations

Affiche graphique latency before/after batching

NOTES:
"Le second composant clé: Sync-Server.

Problème naïve: 100 opérations = 100 messages = 5 secondes latency.

Notre solution: BATCHING INTELLIGENT.

Client types 100 characters fast in 100ms. Nous ne pas envoyer 100 messages.
Nous batch les 100 ops dans 1 message. Envoyé au serveur.
Serveur applique, merge avec autres clients, transmit back.

Résultat: 100x reduction reseau traffic. Latency drops from 5 secondes to 50ms.

Autres optimisations:
- Heartbeat: Detect network partition après 90s
- Session recovery: Reconnect sans perte data
- Document metadata: O(1) lookup by ID
- Message compression: Optionnel pour connections slow

Performance measured: 10,000+ operations par seconde throughput."

SLIDE 18: Pourquoi CRDT difficile

NOTES:
"Beaucoup de systèmes claim support CRDT. Mais beaucoup ont des bugs subtiles.

Raisons pourquoi c'est difficile:

1. DATA LOSS
   Si deux clients modifient offline, une edit peut disparaître.
   Très hard à debug.

2. INCONSISTENCY
   Deux replicas finissent dans des états différents.
   Brisé.

3. CAUSALITY VIOLATIONS
   Si Alice's edit depends on Bob's edit, l'ordre peut être inversé.
   Cause bugs subtles.

4. TOMBSTONE EXPLOSION
   Deleted items = marked deleted, pas vraiment removed.
   Memory grows forever. IDE crash après 1 heure.

5. PERFORMANCE
   Naive CRDT implementation = O(n²) merge.
   Très lent avec gros documents.

Notre solution: LSeq algorithm (proven in academic papers).
Immutable identifiers (guarantee causality).
Tombstone garbage collection (constant memory).
O(log n) merge (efficient).
57 comprehensive tests.

Result: None de ces problèmes."
