1. DÉFINITION FORMELLE
────────────────────────────────────────────────────────────────────────────

Un diagramme de cas d'utilisation est une représentation graphique UML 
(Unified Modeling Language) qui modélise les interactions entre :
  • Les ACTEURS (entités externes : utilisateurs, systèmes)
  • Le SYSTÈME (boîte noire avec frontière)
  • Les CAS D'UTILISATION (fonctionnalités du système)

Formellement : UC = {A, S, CU, R}
  Où :
    A  = ensemble des acteurs externes
    S  = système modélisé
    CU = ensemble des cas d'utilisation
    R  = ensemble des relations (associations, inclusions, extensions)


2. ÉLÉMENTS COMPOSANTS
────────────────────────────────────────────────────────────────────────────

a) ACTEURS : Entités externes qui interagissent avec le système
   Types :
   - Acteur primaire : initie l'interaction (ex: Developer)
   - Acteur secondaire : reçoit les services (ex: Repository)
   
b) CAS D'UTILISATION : Descriptions de séquences d'interactions
   Propriétés : {nom, description, acteurs, préconditions, postconditions}
   
c) RELATIONS :
   - Association : lien direct acteur ↔ cas d'utilisation
   - Inclusion : UC1 --include--> UC2 (UC2 toujours exécutée)
   - Extension : UC1 --extend--> UC2 (UC2 optionnellement exécutée)
   - Généralisation : UC1 est spécialisation de UC2


3. MATHÉMATISATION
────────────────────────────────────────────────────────────────────────────

Pour Distributed IDE, nous définissons :

Acteurs : A = {Developer, LSPServer, Terminal, WebRTC, Repository}

Cas d'Utilisation : CU = {
  WriteCode,
  ExecuteTerminal,
  SynchronizeCode,
  ManageConnections,
  BrowseRepository,
  DebugCode,
  ViewLSPSuggestions,
  HandleConnections
}

Relations d'Inclusion :
  include = {
    WriteCode → ViewLSPSuggestions,
    ExecuteTerminal → HandleConnections,
    SynchronizeCode → BrowseRepository
  }

Relations d'Extension :
  extend = {
    WriteCode ⟿ DebugCode (optionnel),
    SynchronizeCode ⟿ ManageConnections (conditionnel)
  }


4. FORMULE DE COUVERTURE
────────────────────────────────────────────────────────────────────────────

Couverture = |CU_inclus| / |CU_total|
            = 8 / 8 = 100% (tous les CU modélisés)

Complexité = |R| / (|A| × |CU|)
           = 11 / (5 × 8) = 0.275 (modérée)

FORMULE D'INTERACTION
────────────────────────────────────────────────────────────────────────────

Pour chaque cas d'utilisation UC_i :

  Flot principal (Main Flow) :
    1. Acteur primaire initie UC_i
    2. Système exécute séquence d'actions
    3. Postconditions vérifiées
    
  Flux inclus (Included Flow) :
    UC_i ──include──> UC_j
    ∀ exécution de UC_i ⟹ exécution de UC_j
    
  Flux étendu (Extended Flow) :
    UC_i ──extend──> UC_j
    Exécution conditionnelle : UC_j = f(condition)


FORMALISATION DE CHAQUE CAS D'UTILISATION
────────────────────────────────────────────────────────────────────────────

1. WRITE CODE
   ──────────────────────────────────────────────────────────────────────────
   Acteur primaire     : Developer
   Acteur secondaire   : LSPServer (include)
   Préconditions       : IDE open, editor active
   Postconditions      : code modified, suggestions available
   
   Séquence principale :
     1. Developer enters code in editor
     2. System triggers LSP suggestions (include ViewLSP)
     3. Developer receives autocomplete proposals
     4. Code is persisted
     5. Memory state updated
   
   Séquence alternative :
     • Debug mode option (extend DebugCode)
     • If error detected → Debug initiated


2. VIEW LSP SUGGESTIONS
   ──────────────────────────────────────────────────────────────────────────
   Acteur primaire     : LSPServer
   Préconditions       : WriteCode triggered, LSP cache ready
   Postconditions      : suggestions displayed in IDE
   
   Séquence :
     1. LSPManager.getCompletions(uri, line, char)
     2. Check LspCacheManager for cached results
     3. If cache miss → query LSP server (100-1000x faster if hit)
     4. Return formatted suggestions
     5. Update UI with proposals


3. EXECUTE TERMINAL
   ──────────────────────────────────────────────────────────────────────────
   Acteur primaire     : Developer
   Acteur secondaire   : TerminalService, WebRTC (include HandleConnections)
   Préconditions       : Terminal session active
   Postconditions      : command executed, output displayed
   
   Séquence :
     1. Developer inputs command
     2. Terminal process manager validates
     3. HandleConnections protocol (include) established
     4. Command executed in subprocess
     5. Output streamed to terminal
     6. Process cleanup on exit


4. HANDLE CONNECTIONS
   ──────────────────────────────────────────────────────────────────────────
   Acteur primaire     : WebRTC / Terminal / System
   Préconditions       : Connection required
   Postconditions      : Connection established, heartbeat active
   
   Séquence :
     1. Connection request received
     2. WebSocketHeartbeatManager initialized
     3. Heartbeat monitoring started (65s timeout)
     4. Dead connections detected & cleaned
     5. Reconnection logic if needed


5. SYNCHRONIZE CODE
   ──────────────────────────────────────────────────────────────────────────
   Acteur primaire     : Developer
   Acteur secondaire   : Repository, BrowseRepository (include)
   Préconditions       : Git configured, local changes pending
   Postconditions      : Remote synchronized, conflicts resolved
   
   Séquence principal :
     1. Developer triggers sync
     2. System runs BrowseRepository (include) for state
     3. Conflict detection (optional ManageConnections extend)
     4. CRDT sync algorithm applied
     5. Remote updated
   
   Extension :
     • If connection fails → ManageConnections retry logic


6. BROWSE REPOSITORY
   ──────────────────────────────────────────────────────────────────────────
   Acteur primaire     : Repository
   Préconditions       : Git repository accessible
   Postconditions      : File tree displayed, history available
   
   Séquence :
     1. Query JGit for repository state
     2. Build file tree from commits
     3. Calculate diffs for changed files
     4. Display browser UI
     5. Enable file operations


7. DEBUG CODE
   ──────────────────────────────────────────────────────────────────────────
   Acteur primaire     : Developer
   Type                : Extension de WriteCode (optionnel)
   Condition d'activation : Error detected || User requests debug
   Postconditions      : Debugger session active, breakpoints set
   
   Séquence :
     1. Developer activates debug (extends WriteCode)
     2. GlobalExceptionHandler catches breakpoint
     3. Debug symbols loaded
     4. Breakpoints established
     5. Step-through execution enabled


8. MANAGE CONNECTIONS
   ──────────────────────────────────────────────────────────────────────────
   Acteur primaire     : WebRTC
   Type                : Extension de SynchronizeCode (conditionnel)
   Condition           : Network issues detected
   Préconditions       : Connection state = unstable
   Postconditions      : Reconnected or graceful fallback
   
   Séquence :
     1. WebRtcConnectionManager.autoReconnect() triggered
     2. Exponential backoff: 1s → 5s → 10s → 30s
     3. Max 10 attempts before timeout
     4. IceCandidateBuffer manages pending messages
     5. Recovery or fallback to polling mode


RELATIONS FORMELLES
────────────────────────────────────────────────────────────────────────────

Include Relations (Mandatoire) :
  WriteCode              ⊢ ViewLSPSuggestions
  ExecuteTerminal        ⊢ HandleConnections  
  SynchronizeCode        ⊢ BrowseRepository

Extend Relations (Conditionnel) :
  WriteCode             ⟿ DebugCode          [if error_detected]
  SynchronizeCode       ⟿ ManageConnections  [if network_unstable]

Précédence :
  DebugCode ⊂ WriteCode (debug ne peut s'exécuter seul)
  ManageConnections ⊂ SynchronizeCode
